# S5-R fabrication renders (DND-69)

Board-viewable PNG renders of the **S5-R** printable part set and the assembled
per-cell register. Generated by
[`../tools/render_images.py`](../tools/render_images.py) from the committed
OpenSCAD-produced STLs in [`../stl/`](../stl/).

**Evidence class: CAD render of the committed OpenSCAD meshes. NOT a print and
NOT a measurement** ([DND-27](/DND/issues/DND-27)). These images visualise
geometry; they validate nothing physical. No part has been printed and none
will be — the board performs the first physical print.

## Assembled mechanism

The per-cell register as it sits in the field: 3 × 3 cell cluster with **rotor**
(blue), **drive pawl** (orange), **keeper** (green) and **detent leaf** (violet)
installed on the **rack strip** (gold) with the **sourced Ø6 steel drive rod**
(grey, not printed).

## Reproduce

```sh
pip install numpy pillow
python 08-current-design/fabrication/tools/render_images.py         # -> images/
python 08-current-design/fabrication/tools/render_images.py --check # verify
```

Each image filename is `<part>_<view>.png` (`iso` / `front` / `top`). The
machine-readable record is
[`../manifests/render_images_record.json`](../manifests/render_images_record.json).

## How these renders are made (and why not OpenSCAD's PNG backend)

The committed `stl/*.stl` are produced by **real OpenSCAD**
([`render_fab_parts.py`](../tools/render_fab_parts.py)) and every PNG here is
rasterized from **those exact meshes**, so the images are true to the shipped
geometry.

OpenSCAD's *own* PNG backend needs an OpenGL context. In the agent container
there is no display and no GPU (the offscreen Qt platform reports
`Can't create OffscreenView: Unable to obtain GL Context`), so OpenSCAD can
render STL but cannot rasterize a PNG. `render_images.py` therefore rasterizes
the OpenSCAD meshes with a small software renderer (numpy + Pillow): z-buffered,
flat-Lambert shaded, deterministic camera. It needs no GL, no X and no OpenSCAD.
